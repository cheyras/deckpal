## 2026-10-10 — Scanner: a printed name that names another card questions a confident printed number
**Decided by:** Chey (via Claude Opus 5.5)

**Decision:** A confident resolve answer keyed on the printed number (`badge+number` or `number+denominator`, one card) is now reviewed after the climb. This happens only when the printed name does not agree with that card AND the name positively points at a different card. The review is `letTheNameQuestionTheKey` in `apps/api/src/scan/resolve.ts`.
- **The picture and the title agree on a different card.** The vector is decisive for card V, and the read name agrees with V's name (`nameAgrees`). If V also fits a printed field of the key that was not in doubt, V is the answer, resolved as `corroborated`. "Fits" means V carries the number read, or V is in the badge's set, or (for a `number+denominator` key only) V's set prints the denominator read. If V fits none of those, the answer becomes unconfident with both cards, because overruling would mean believing two printed fields were both misread.
- **The title and the denominator name a different card.** No picture is needed for this one. The read is a catalogue name, exact or missing its rule-box suffix (tier 0/1), of a card in a set of the denominator read. For a `badge+number` key, only cards in the badge's own set count. The answer becomes unconfident and lists the keyed card plus those rivals, with the keyed card pinned through the 25-card cut. A vector top-1 inside that list still corroborates, as on any key-narrowed list.
- **Disagreement alone changes nothing.** A garbled title (`Polcemon`, `sic Pokemot`) agrees with no card, so it never costs a correct number its confidence. The vector alone still never reviews a key (fuse.ts rule 1).
- **The review stands down** when the near-exact dHash names the keyed card, when the vector's own top-1 is the keyed card at `showable` or better (the bar `corroborate` uses for agreement), when the read is a whole-word piece of the keyed card's own name (`readIsFragmentOf`: `Charizard EX` off `M Charizard EX`, `Kyogre EX` off `Primal Kyogre EX`, `Switch` off `Energy Switch`, `Dialga` off `Dialga G`), and when the read is itself the exact name of a third card (the existing `Marill`/`Azumarill` guard, now one shared helper).

**Why:** The owner's verified photos had a Charizard ex secret rare, sv03-223, printed `223/197`. OCR read `Charizare` and `23/197`, dropping the leading digit. sv03 is the only 197-card set, so `23/197` is exactly one real card, sv03-023 Capsakid, and rung 3 returned it confident. The vector meanwhile was decisive for sv03-223 (0.873, margin 0.068 on the live model; 0.781, margin 0.305 on the fine-tuned one). The existing dropped-digit fixes (`name+denominator`, `letDecisiveVectorSpeak`) only run when the bad number names zero or several cards, so a dropped digit that lands on one real card ended the climb confident. Benchmark, live vectors (`vit_base_patch32_clip_224.openai`):
- **Default bench (244 cards):** AUTO-ID 168/244 (68.9%) and WRONG 1/169 (0.6%), both unchanged. No row changed.
- **Owner's verified quad photos (218 cards, `quad-verify`):** AUTO-ID went from 82 to 83 (37.6% to 38.1%) and WRONG from 23/105 to 22/105 (21.9% to 21.0%). Exactly one row changed: the Charizard, now confident and right.
- **Same quad photos with the fine-tuned vectors (#288, not yet live):** AUTO-ID went from 106 to 107 (48.6% to 49.1%) and WRONG from 21/127 to 20/127 (16.5% to 15.7%). Again the one row that changed was the Charizard.
- **Afterwards, no confident wrong answer on either bench comes from a number-keyed rung.** What remains is dHash, vector and corroborated answers.

**The PR #297 review's guards, and why each one exists.** All three were verified on the real catalogue before the fix. After it, both live-vector benches above are byte-for-byte the same rows (0 changed on each), because no bench capture hits them.
- **A badge names one set.** `PAR 161/182` read with the title `Team Rocket's Giovanni` (a card only sv10 prints, and sv10 also has 182 cards) demoted sv04-161. With a decisive vector on sv10-174 it became a confident sv10-174, overruling the badge AND the number on the strength of the denominator they share. Now no rival is taken from outside the badge's set, and V from another set fits a badge+number key only by carrying the number read. That case is now a question with both cards.
- **A piece of the keyed card's own name.** M Charizard EX `108/106` read as `Charizard EX` demoted xy2-108 under xy2-11/12/100, and a showable, separated vector on xy2-11 then made it a confident wrong answer. This is systematic wherever a set prints a card and its variant: a sweep of the bench catalogue found 196 uniquely-keyed cards with a whole-word piece of the name that is another card's name in a set of the same size, and the review had demoted 173 of them. After the fix it demotes none. The reverse (a read holding the whole keyed name plus a word, like `Rotom Dex` read when `Rotom` is keyed) is deliberately not a fragment: OCR loses words and keeps junk, it does not add a real word.
- **The vector agreeing with the key is agreement at `showable`.** Before, only a decisive vector on the keyed card stood the review down. A showable one let the title-and-denominator branch demote a correct key, or relabel it `corroborated` when the vector was also separated.

**Implications:**
- **Rule 1 is narrowed.** The module header's "a key that resolved is never reviewed" now reads "never reviewed by the vector alone". A future change that lets the vector demote a key with no name read, or lets a merely disagreeing name do it, is a different decision and needs its own benchmark run.
- **The title-and-denominator branch runs with `SCAN_EMBED_MATCH` off.** It reads only print (title + denominator), so a flag-off deployment takes it too. Every rule that uses an image signal still needs the flag.
- **One more `card` scan on part of the confident number-keyed answers.** When the name read disagrees with the keyed card and no stand-down applies, the review runs `byName`, which scans `card` in production. That is not rare by construction: a review count put it at about half of confident number-keyed answers (37 of 78). Measured with temporary instrumentation on the scan bench (live vectors), it ran on 0 of 14 such answers on the default bench and 1 of 9 on the owner's quad photos with these guards in place (0 and 2 before them). So budget for the higher figure and expect the lower. Rung 5b and both post-climb reviews share one memoised lookup, so a request pays at most one scan.
- **Merge note for PR #294 (reprint guard).** #294 also rewrites the end of `resolveCard`. The correct combined form is:
  ```ts
  const reviewed = out.confident ? await letTheNameQuestionTheKey(out) : opts.fusion ? await letDecisiveVectorSpeak(out) : out;
  return opts.artSiblings ? await openThePrinting(reviewed, opts.artSiblings) : reviewed;
  ```
  This PR already ends with that `reviewed` expression and no early return, so the printing guard drops in on the `return` line and sees every answer. Two things the merge should know. First, the picture-and-title branch's hand-built `corroborated` answer carries no `keyedBy` (#294's internal field), so `openThePrinting` treats it as not keyed and will open the printing if the corroborated card has same-art siblings. That is arguably right, since the key it overruled is the one that would have decided the printing, but it should be a choice. Second, the title-and-denominator branch goes through `done`, so it gets `keyedBy` from #294's `keyedFrom`. Its `cards` argument is the full keyed+rivals list (the pin happens inside the cut), so `keyedFrom`'s "the whole keyed list survived the cut" test stays truthful.
- **Tests:** sections 5 and 6 of `apps/api/src/scan/__tests__/resolve-field-fixes.test.ts` pin the Charizard case, the negative guarantees, and the review's guards (badge set, fragments, showable agreement, the pinned keyed card, one name lookup per request).
