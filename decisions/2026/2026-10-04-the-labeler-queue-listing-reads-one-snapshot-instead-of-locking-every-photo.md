## 2026-10-04 — The labeler queue listing reads one snapshot instead of locking every photo
**Decided by:** Chey (via Claude Opus 5.5)

**Decision:** `GET /dev/scan-queue` builds the queue from ONE object listing of `dev-queue/` (both buckets). For each family that listing saw with a photo, the snapshot picks what to show: the replacement JPEG if it was listed, else the original, with the size the listing reported. Only that photo's sidecar is then read (else the original's), with no lock, at most 8 at a time. A family the listing saw only as sidecars is still rechecked at its photo paths under the family lock, two at a time, as before. Reads, repair, cleanup, discard, enqueue and the capture migration keep the family lock unchanged. The response shape and its oldest-first order are unchanged. `QueueStore` gains `list()`, so the listing and its 502-on-outage mapping live in the queue layer instead of the route. A sidecar already read is answered from memory only while the listing reports the same etag for it, and only when that etag is the MD5 of the bytes that were read. Each sidecar read gets 5 s per attempt, not the 20 s default (`CaptureStore.read` takes a per-call `timeoutMs`). A throttle (429), a 5xx, a timeout or a dropped connection is retried twice with backoff, and so is a failed object listing. A refusal fails immediately.

**Why:** Measured 2026-10-05 UTC, the route answered 504 FUNCTION_INVOCATION_TIMEOUT on every call, and nothing (labels or scanner telemetry) had reached `/dev/scan-flags` since 2026-09-27 22:48 UTC: the owner could not work the queue at all. The 2026-09-26 design took the family lock for every listed photo, two at a time, and inside it made up to two Storage HEADs and one or two sidecar reads. The private bucket (2026-09-28) made each absent-object probe three requests, because the read-through checks private, then legacy, then private again. That came to about 0.3–0.8 s per photo, so a few hundred photos passed Vercel's 60 s limit. Now a photo costs one sidecar read the first time and nothing after, with no database round trip. Locking an unlocked read buys nothing. The listing only ever answered "what was here when I looked", and by the time the reader sees it that answer can be stale with or without the lock. What the lock protects is what happens when a photo is opened or changed, and those paths keep it.

The rest came from verifying on the PR preview, where the queue held 1036 photos. At 16 reads in flight, warm listings answered in 6.5–9 s, but two things went wrong. The first cold call answered 502 after 32 s, because one sidecar read waited out the 20 s timeout. And the listing right after a cold run got a fast 502 from the object listing itself, while the next one slowed to 15 s: Supabase was throttling the burst. object-store.ts had already measured `429 too_many_connections` at six parallel uploads. The labeler re-lists after every label and every discard, so without the memory, each label would also have fired about a thousand reads at the Storage service the whole product shares. Hence 8 in flight, a quick retry instead of a lost listing, and no repeat reads of sidecars whose bytes have not changed.

**Implications:** The 2026-09-26 guarantees still hold. A photo the snapshot saw is never hidden, because nothing drops a family with a listed photo. A sidecar alone is still not a photo. Each family appears once, under its original ID. A photo the listing missed is still found by the locked recheck, as long as its sidecar was listed. The one thing that moved: a listing that runs while a discard is in progress can now show the discarded photo once, because it no longer waits behind the lock. Opening that entry is a locked read that answers 404, repair has no source to bring it back, and the next listing drops it. Same-device read-your-writes holds: the labeler refreshes only after its delete returns, and the Storage listing is a database query. The sidecar memory is per server process and content-addressed. A hit returns exactly what reading the listed bytes would, a rewrite lists a new etag and is read afresh, and locked reads never use it. If Storage ever stops reporting MD5 etags, the memory stays empty and every listing reads every sidecar again (correct, only slower). Sizes come from listing metadata, and only the queue's byte total uses them. A stale entry can show the original's size or metadata until the next refresh, and its ID always opens the current photo. Tests now pin the call counts:
- no lock and no photo probe for a family whose photo was listed
- one listing plus one sidecar read per photo across 500
- zero sidecar reads on a warm re-list of 500, and only the changed sidecar after a rewrite

They also pin peak concurrency (8 sidecar reads, 2 locked rechecks), the retry and fail-fast ladder, and the stale-entry read. The state table in `apps/api/src/dev/queue-state.md` describes the new listing.
