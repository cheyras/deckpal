## 2026-09-22 — A metered deep refusal is terminal for the turn, not a retry invitation

**Decided by:** DeckPal Todoist implementation worker on behalf of @cheyras

**Decision:** Once the deep meter has refused a call in a user turn, that refusal stands for the rest of the turn. `buildDeepTools` now carries a turn-scoped refusal ledger (`apps/api/src/decke/meteredRefusals.ts`) read by three places that cannot disagree: `needsApproval` raises no second approval card, `execute` refuses before reaching the meter even if a call is forced, and `api/chat.mjs`'s `prepareStep` drops the deep tier from `activeTools`. `deepRefused` tags meter refusals with a `[meter:cap|hold|credits]` token so the verdict survives the browser's approval legs, where `api/chat.mjs` reconstructs every tool from scratch and an in-memory closure is empty.

**A call's identity excludes what the server added to it.** `needsApproval` injects `no_research: true` into an unbacked `write_strategy_guide` input so the approval card can show the reader the guide is not backed by research, and `execute` then sees the mutated object. Keying the ledger off that made a refusal unrecognisable the moment the model re-emitted its original `{deck, findings}`, and a second card went up for identical work — the loop this ledger exists to close, surviving inside it. The fingerprint now strips server-injected keys on both write and read. A different deck, different findings or a different tool is still different work and stays askable.

**The browser carries the evidence, because the server keeps none.** The refused call used to leave no trace on the next POST: `useDeckeChat.ts` replayed lookup summaries and `output-error` parts and matched the SDK's `tool-output-available` chunk with nothing, so the seed was correct and permanently empty on exactly the leg that mattered. `apps/web/src/character/host/chat/meterRefusal.ts` now carries the refused call — tool-call id, original input, the server's own refusal text — and nothing else, as the SDK's `output-available` UI part. It rides in the leg prefix, ahead of the approval answers, because the SDK collects approvals from the final parts of the final message. Identity is seeded from the outgoing wire rather than the reply: a resumed approved call streams its output with no new `tool-input-available`, so on the continuation leg the request is the only place the call's name and arguments still exist. Bounded at four refusals and 600 characters each; ordinary results are not replayed, since a deck read is kilobytes re-billed on every later leg.

**Scope of a refusal:** A spent daily cap or a held wallet is a property of the tier — all four deep tools become impossible and leave `activeTools`. An insufficient-credit refusal is a property of the call — only the identical `(tool, args)` call is blocked, a cheaper deep tool still asks normally, and the tier stays in view. Free reads, writes, cosmetic tools and every non-deep capability are untouched in both cases. Only a real meter verdict is recorded: `charge` fails open when the database is unreachable, and a provider fault takes the `deepFailed` path and carries no scope, so a transient 503 can never read as a spent meter.

**Reset semantics:** The ledger is seeded per request from the replayed history after the reader's last message, so it is turn-scoped and user-scoped with no module-level state. A new user message is a new turn: the leg wire is discarded at the turn boundary, later turns are rebuilt from chip summaries that carry no meter token, the seed comes back empty and the meter is asked for real — which is the only way a top-up, a refund or tomorrow's reset takes effect. There is no permanent lockout and no cross-user leakage.

**Safety unchanged:** Independent signed approvals keep their ordering and signatures across the refusal leg; human-decline behaviour is untouched (`declined.ts` strings carry no meter token and are never read as one); budgets, error and refusal chips, and the honest `[[NO_WORK]]` non-narration all stand. Nothing auto-approves a write. Both the browser reader and the server seed accept only `tool-…` parts whose output matches the anchored marker this codebase emits, so no amount of model prose can suppress work the meter would have allowed.

**Verification:** 16 behavioural tests in `apps/api/src/decke/__tests__/meteredRefusals.test.ts` drive the real `buildDeepTools`, `focusedTools` and `streamText` with a local `MockLanguageModelV3` and a gateway that throws: first refusal, duplicate suppressed before both the card and the charge, the injected-flag fingerprint proven with freshly built argument objects in memory and across a replayed POST, sibling suppression under a tier-wide cap, credits refusals leaving affordable siblings alone, a spent tier withheld from the SDK, a forced call refused inside the SDK loop with zero second charge, new-turn reset, cross-user isolation, and a transient provider failure not being terminal. 10 tests in `apps/web/src/character/host/chat/__tests__/meterRefusal.test.ts` pin what travels; 3 source pins in `legWiring.test.ts` and 2 in `chatWiring.test.ts` pin the call sites at both ends. The end-to-end regression is a Playwright fixture (`tests/browser/chat.mjs`, `tests/browser/fixture.tsx`) that drives the real `useDeckeChat` over a real `fetch('/api/chat')` against a mocked SSE stream, gives consent through the real approval card twice, captures the next request body off the wire and feeds it to the real `seedMeteredRefusals` and a brand-new `buildDeepTools`: the repeated guide raises no card, reaches no meter and reaches no provider, a different affordable call still asks, and a new user turn asks again. Measured: `apps/api` decke suite 509/509, `apps/web` DeckE suites 698/698, both typechecks clean, focused real-browser check passing at 1280 and 390. Negative control: removing the leg-prefix carry, removing the wire-seeded call identity, and removing the fingerprint normalisation each fail the browser regression and their own pins; none was kept. The `Browser boundaries` CI workflow now also builds `@deckpal/db` and `@deckpal/agent-tools`, in that dependency order, before running the browser suite, so the workflow's own build step produces the server-proof dependencies `tests/browser/meterReplayProof.mts` imports instead of relying on artifacts left over in a local checkout.
