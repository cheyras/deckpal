## 2026-09-19 — Fix SetHeader release date showing Sep 15 instead of Sep 16 in America/Denver
**Decided by:** release-date worker (Claude Sonnet 4.6) on behalf of @cheyras
**Decision:** Add an explicit `fmtCalendarDate(iso)` helper in `apps/web/src/lib/format.ts` for SQL DATE / catalog release-date contexts and route the five catalog release-date consumers through it: `components/SetHeader.tsx`, `routes/CardDetail.tsx`, `routes/SeriesIndex.tsx`, `routes/SeriesDetail.tsx`, `components/UpcomingSetRow.tsx`. `fmtCalendarDate` accepts bare `YYYY-MM-DD` strings and exactly midnight-UTC serializations (`YYYY-MM-DDT00:00:00Z` and `YYYY-MM-DDT00:00:00.000Z`) — both name a calendar day, not an instant — and builds the Date from the calendar parts in the local zone, preserving the round-trip overflow check and the em-dash fallback for null/invalid/non-midnight inputs. `fmtDate` is restored to its genuine timestamp behaviour: bare `YYYY-MM-DD` keeps its calendar-day path (existing API contract), but anything with a time or offset is a true instant and converts to the local calendar day — so a `T00:00:00Z` midnight timestamp lands on Sep 15 in America/Denver, which is correct for admin/audit/credit/list/deck history users. New `node:test` cases cover the side-by-side `calendarSep16` vs `trueInstantSep15` regression under Denver, calendar values across UTC/Auckland, and null/invalid/overflow for both helpers.
**Why:** A prior date worker had instead extended the global `fmtDate` to reclassify ANY midnight-UTC timestamp as a calendar day. That fixed the 30th Celebration release tile (Sep 16) but silently violated timestamp semantics for every genuine-instant consumer — admin events, audit rows, credit entries, list/deck history all shifted a day early in zones behind UTC, because the live API serializes those as `T00:00:00Z` too. The release-date bug is narrow to SQL DATE columns (which the API happens to serialize as midnight UTC); the right fix is to make that narrowness explicit at the call sites that read SQL DATE columns, not to redefine what a timestamp means globally. The original defect was that `SetHeader` rendered `Sep 15, 2026` for the 30th Celebration release date (`2026-09-16`) in Denver because the midnight-UTC form fell through to `fmtDate`'s instant branch; `fmtCalendarDate` pins the calendar day for that one consumer.
**Implications:** `fmtDate` no longer special-cases midnight-UTC; it is back to instant-to-local-day conversion everywhere except bare `YYYY-MM-DD`, so admin/audit/credit/list/deck history timestamps read correctly in every timezone. The five catalog release-date call sites now use `fmtCalendarDate`, which renders `Sep 16, 2026` for `2026-09-16` and both midnight-UTC serializations in UTC, America/Denver and Pacific/Auckland. Any other SQL DATE column surfaced in the UI should use `fmtCalendarDate` at its call site; genuine timestamps must keep `fmtDate`. The fix was verified by Playwright screenshots of `/series/mega-evolution/30th` at 1440 px and 390 px with `timezoneId: 'America/Denver'` (both viewports show `Sep 16, 2026`) and by the unit-test regressions.
