## 2026-09-19 — Remove PR190 ad-hoc psql sync_run step; cloud snapshot tracking routes through the application wrapper
**Decided by:** final-integration worker (Claude Sonnet 4.6) on behalf of @cheyras
**Decision:** Remove the `Record snapshot-collection sync_run` comment block and `psql -c INSERT INTO sync_run …` step that a temporary recovery PR (#190, commit 4e3e8968) added to `.github/workflows/price-refresh.yml` after the `pnpm --filter deckpal-sync prices snapshot` step. The sole tracking authority for the cloud snapshot path is now `runCloudSnapshot` in `apps/sync/src/jobs/cloudSnapshot.ts`, already integrated and called by `prices/cli.ts` (verified implementation recorded in snapshot-repo DECISIONS.md 2026-09-19, "Fix cloud snapshot health not updating after successful cloud runs"). The actual `pnpm --filter deckpal-sync prices snapshot` invocation, the `*/15`, `10 2 * * *` and `10 21 * * *` schedules, the `workflow_dispatch` job/force inputs, the credentials preflight, the pnpm/Node setup, the `PGPOOL_MAX=1` pool budget, the `Build @deckpal/db` step, the no-reconcile commentary and the job-summary step are all retained unchanged.
**Why:** PR190's step was success-only bookkeeping written before `cloudSnapshot.ts` existed: it inserted `('snapshot-collection','ok',now(),0)` only when the prior step succeeded, so it always reported `rows_written=0` regardless of how many `collection_value_point` rows were actually written, and on a wrapper SKIP that exits 0 (lock busy or an active `sync_run`) it would still record `ok` — a false completion; on an actual failure the wrapper re-throws, the CLI exits 1 and the workflow's success-only SQL step is skipped, so it cannot record `ok` after a failure. The application wrapper instead acquires the `snapshot-collection` advisory lock, opens a `sync_run` row via INSERT … ON CONFLICT DO NOTHING (respecting `sync_run_one_active`), calls `snapshotAllUsers`, and closes the run as `ok` with the actual insert count or as `failed` (re-throwing) on error — the same lifecycle every other sync job uses. Keeping both would write duplicate `sync_run` rows on success (the SQL's later `rows_written=0` row overwriting the wrapper's real last-success count) and, on a wrapper SKIP that exits 0, would record a false `ok` completion; a failure re-throws, the CLI exits 1 and the success-only SQL step is skipped, so no `ok` row is written after a failure.
**Implications:** `price-refresh.yml` no longer duplicates the wrapper's bookkeeping; `runCloudSnapshot` is the sole `sync_run` authority for the cloud snapshot path. Production verification of the wrapper has NOT been performed: it requires one successful `workflow_dispatch` of `price-refresh` (job: `snapshot`) followed by `GET /api/health` showing a fresh `snapshot-collection` last-success timestamp with the actual `rows_written` count, including zero for a same-day rerun. This uncommitted patch still needs full GitHub CI (including the database-integration boundary) before merge.
