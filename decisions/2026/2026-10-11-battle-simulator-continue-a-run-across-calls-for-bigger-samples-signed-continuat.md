## 2026-10-11 — Battle simulator: continue a run across calls for bigger samples (signed continuation token)
**Decided by:** @cheyras (a 25 s call plays only about 25 strong or 120 fast games, so intervals stay wide; wanted a bigger sample without new infrastructure); built by Claude Sonnet 5.5.

**Decision:** A `POST /decks/simulate` run can be continued by a later call that adds games on new seeds and reports the cumulative result. The server keeps nothing: each response carries a `continue_token`, and the client sends it back with the same inputs.

- **Token.** `sc1.<payload>.<mac>`; the payload is JSON, deflated, base64url (about 250 characters for a two-opponent plain run, a few hundred to a kilobyte for a paired comparison). It holds: format version (1), issue time, calls so far, speed, seed, kind (plain or paired), a deployment stamp, an IDENTITY (12-character SHA-256 fingerprints of the subject's resolved card list, version B's, and each opponent's in order, plus the format when a list needed resolving), and the running TOTALS per opponent: the next unplayed seed pair, record (wins, losses, draws, time-outs, errors), the decided wins and losses behind the win rate, the going-first and going-second splits, summed turns over finished games, win and loss reasons, the opening-speed counts (attacked, attacked by turn 2, mulligans) for both sides, and the loss-pattern counts. For a paired comparison each version has those totals, and each opponent also keeps the sufficient statistics of the paired interval: clusters, Σn, Σd, Σd², Σd·n, Σn², and the B-ahead and A-ahead counts. Code: `packages/sim/src/continue.ts` (totals, merge, wire form, cumulative reports) and `apps/api/src/deck/simulateContinue.ts` (token, signature, identity).
- **Same games as one longer run.** `runSimulation` / `runPaired` take `firstPair`: pair `firstPair + k` plays the seed `deriveSeed(seed, firstPair + k)`, the seats and the pilots a single longer run gives it. Each opponent continues at its own `next` (a call that hit its time budget may have got further against some opponents). A test runs the same batch as one run and as two or three continued calls and checks the game summaries are identical, the totals are identical, and the cumulative overall and per-opponent numbers equal the long run's.
- **Paired interval is exact.** `diffOf` now computes the cluster-robust interval from the sums (`PairedStats`), via Σ(d − r·n)² = Σd² − 2rΣd·n + r²Σn². Every cluster sum is a multiple of ½ and every n a small integer, so the sums are exact in floating point and independent of the order they were added in; a test checks the merged statistics, interval, counts and verdict deep-equal the long run's, and the existing comparison tests are unchanged.
- **Integrity.** HMAC-SHA256 over a domain label, the caller's user id and the compressed payload, truncated to 128 bits, keyed by a key derived from `DECKE_APPROVAL_SECRET` (the secret Deck-E's signed approvals and Deep Think tokens already use; no new variable, so no infrastructure change). The mac is checked before anything is inflated or parsed. A client cannot forge or edit totals, and cannot use another account's token. Unset secret = continuation is off, the same fail-closed stance as Deep Think: no token is issued, a call carrying one is `503 continuation_unavailable`, the existing boot warning names it and `GET /health` already reports `deckeApprovals: "unsigned"`. `DEPLOYMENT.md`'s `DECKE_APPROVAL_SECRET` row says so (B11).
- **Identity checks.** The decks are re-resolved and fingerprinted on every continued call and compared with the token's: a deck edited between calls, another opponent set or order, a different kind (plain vs comparison), version B, format, speed or seed is a `400` that says what differs and that a fresh run (no token) is the way on. `speed` and `seed` may be omitted on a continued call and then come from the token. Also refused with a message: a bad signature or shape, another token-format version, a token older than 2 hours (every response issues a fresh one), a token issued by an earlier deployment (the stamp is a hash of `VERCEL_DEPLOYMENT_ID` or `VERCEL_GIT_COMMIT_SHA`, system variables the platform sets, so a deploy that changes the engine never blends with older totals), and a chain past 12 calls (the 12th response carries no token).
- **Cumulative report.** The text says "Cumulative over 3 calls: 92 games (30 added by this call)…" and every rate has its n and interval at the cumulative n; a comparison leads with the verdict a single long run would give. Dropped from a cumulative report, because they do not add up and keeping them would put a table per card in the token: card impact (and changed-card impact), the Prize-taker and liability rows, and the median first attack. The first call's report still has them, and the cumulative text says what it leaves out. The token and a one-line instruction ("call again with the SAME inputs plus continue_token=…; stop when the intervals are narrow enough or the verdict is clear") are the last line of the text, which stays within the 5,000-character limit (the report is rendered into the room the line leaves).
- **Tool.** `simulate_battles` gains `continue_token`. When it is given the other inputs must be given again, the same (not ignored): the token cannot hold the decks, the API re-resolves them and refuses a mismatch, and an assistant that repeats its own arguments does exactly that. `games` then means games to add. The tool description teaches when to continue (the user wants more certainty, or the verdict is still open) and when to stop (clear verdict, narrow intervals, a few calls at most). Still read-only: nothing is stored. Deck-E's `deck_iterate` pathway text tells him to continue the same run for more certainty, at most three continuations, and the `deck_build` text points to it.

**Why:** A call can only afford a few dozen games, which is why a one- or two-card change usually reads "no clear difference at this n". More games means more calls, and the infrastructure rule (no new table, queue, cron or longer function) leaves only client-held state. A totals-only token is small enough to travel through a model's context, merges by addition, and a signature keeps a client from putting numbers into a report that reads as the engine's. Replaying the games instead of keeping totals would cost the same 25 s again; keeping per-game summaries would make the token tens of kilobytes.

**Implications:**
- Replay and branching are not prevented, only forgery: a client can go back to an earlier token and continue from it twice, and two branches are never merged (each is real engine games). The 12-call cap and the existing per-account gate and 6-calls-a-minute rate limit bound the cost; each continued call takes its own gate slot.
- Rotating `DECKE_APPROVAL_SECRET` invalidates tokens in flight (they last 2 hours); nothing else changes. A change to a card script or the engine that is not a deploy carrying `VERCEL_DEPLOYMENT_ID` (self-host) is not detected; the 2-hour life is the bound there.
- A half-played seed pair (the hard deadline cut it) counts as consumed, as it would in one long run, so the next call starts at the next pair. Pairs are therefore not always whole in the totals, only in a run that finished.
- To keep the token small, a new per-run aggregate must be a sum that fits in a few numbers. Anything that does not (a median, a per-card table) belongs in the first call's report, not the token.
- The paired interval's one known looseness (clusters of different opponents share the subject's shuffle) is unchanged.
