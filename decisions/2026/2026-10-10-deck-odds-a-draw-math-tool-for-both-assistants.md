## 2026-10-10 — Deck odds: a draw-math tool for both assistants
**Decided by:** @cheyras (the feature); Claude Opus 5.5 (the design), on behalf of @cheyras

**Decision:** A new read-only agent tool, `deck_odds` (`packages/agent-tools/src/tools/deckOdds.ts`), registered right after `check_deck`, so it reaches the MCP server and Deck-E from one definition. It calls a new `POST /decks/odds` (`apps/api/src/routes/deckOdds.ts`), which runs a pure, seeded Monte Carlo in `apps/api/src/deck/odds.ts`. The tool takes exactly one of `deck_id` (UUID or name, resolved by `needDeck`), `cards` or `ptcgl_text` (check_deck's shapes and resolution), so a hypothetical list can be tested without saving it. It also takes up to 12 `queries` (`{ label?, all_of: Group[1..6], by_turn? 0..10, prized? }`, with `Group = { cards?, kinds?, count? }`; a group is an OR over names and kinds, and a query is the AND of its groups), `trials` (default 50,000, cap 200,000) and `seed` (default fixed at 60). The model is the Standard setup: draw 7, redraw while there is no Basic, set aside 6 Prizes, then one draw per turn, turn 1 included. So hand odds are for the kept hand, and "by turn N" means the hand plus N draws. With no queries it reports each card name: at least one copy in the opening hand, seen by turn 2, prized, and every copy prized. Every answer states the method, trials and seed. It gives the mulligan rate both simulated and closed-form, a 95% margin for each value, and the exact hypergeometric value for any single-group query. It always ends with a caveat that it is draw-only. The Deck-E prompt gains one paragraph: odds come from `deck_odds`, never from your head. `POST /decks/check` and `POST /decks/odds` join `POST /massentry` in `READ_ONLY_POSTS`.

**Why:** The owner once had Claude "run 60,000 drawings of an opening hand and evaluate what percentage of those were setting me up well". Deck-E cannot run code, and a claude.ai session does that ad hoc, differently each time, with no stated method. A fixed seed means asking twice gives the same answer. Every trial also deals the same depth (hand, Prizes, ten draws) whatever was asked, so the default report and a single question share their games and agree exactly. The simulation is the contract, because AND-of-groups queries have no tidy closed form. Single groups get the exact value as well: the kept hand is summed over its composition (matching Basics, matching non-Basics, other Basics, the rest), and one hypergeometric term then finishes the Prize or draw zone. That makes the simulator testable against arithmetic rather than against itself. Over five seeds at 200,000 trials, every query landed within |z| < 2 of the exact value. Unknown card names fail and list the deck's real names. A list the catalog cannot resolve fails rather than guessing, because one unknown Basic would move every number. A list that is not 60 cards, or has more than 4 copies of a card, is still a fair question, so it is computed and the answer says so. The read-only allowlist entry fixes a real defect found while wiring this: ever since `check_deck` shipped (#267), a read-only connection (migration 075) had been offered it and then refused it with 403, because its POST was never added beside `/massentry`.

**Implications:**
- Tool count is 26 (15 read, 11 write). The pins in `readOnly.test.ts`, `landingCopy.test.ts`, the landing copy and llms.txt, README, SECURITY, DEPLOYMENT, ARCHITECTURE, AGENTS and `apps/mcp/SPEC.md` (§5 entry 8b) moved together. Stale 24/21-tool claims in DEPLOYMENT, SECURITY, ARCHITECTURE and the CI comment were corrected at the same time.
- Performance: one index array and partial Fisher-Yates (`partialShuffle`, added to `testhand.ts`, whose own `shuffle` is untouched so seeded test hands do not change). A trial allocates nothing and costs at most 23 RNG draws. Measured on the real 60-card deck: the default report for 50,000 games takes about 40 ms, and 12 six-group queries for 200,000 games take about 75 ms. The request holds its RLS connection for that time. No route-specific rate limit was added; the 200,000-trial cap bounds the work.
- It plays no cards. Search and draw cards count only when named in a group. The coming battle simulator is meant to answer in the same shape: method, sample, seed, margin.
- `routes/decks.ts` exports `loadDeckEntries`, the deck page's own loader, and `routes/deckCheck.ts` exports `resolveInputLines`, so "your deck" and "this list" mean the same cards they mean everywhere else. The deck-check route's behaviour is unchanged.
- Verified end to end before merge. The built API was run on a disposable Postgres 16 with every self-host migration applied and the owner's 60-card "Hide 'n' Sneak" list seeded from its public card facts. The built tool was called over HTTP: deck by name, unsaved list by card id, query and default report, and unknown-name failure. It was not run against production, which still runs the previous code.
