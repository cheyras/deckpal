## 2026-09-28 — Scanner and labeler captures move to a private bucket
**Decided by:** Chey (via Claude). Chey asked for the fix on 2026-09-28.

**Decision:** The scanner's and labeler's captures — quad-labeler photos and labels, the scan harness's "Flag frame" captures, the product scanner's capture/lock/identity reports, their JSON and comment sidecars (`dev-flags/`), and the labeler's pending photos (`dev-queue/`) — move out of the public `card-art` bucket into a new PRIVATE bucket, `dev-captures`. Every read, list, write and delete goes through `CaptureStore` (`packages/storage/src/capture-store.ts`) with the server's service key on Storage's authenticated object route; the browser only ever gets the bytes from the labeler-gated `/dev/scan-flags` and `/dev/scan-queue` routes, as `private, no-store` responses. The objects already in `card-art` are moved by `migrateLegacyCaptures` (`capture-migration.ts`), exposed as `POST /dev/scan-queue/migrate-captures` and called in the background by `/dev/quad-labeler` and `/dev/quad-harvest` until it reports `done`.

- **The bucket creates itself.** `ensureCaptureBucket()` reads `GET /storage/v1/bucket/dev-captures` and, if it is missing, creates it with `public: false`, then re-reads it and refuses to store anything unless `public === false`. Memoised per warm process; a concurrent creator's "already exists" is success. Not a migration: nothing applies migrations on a deploy here (`pnpm migrate` against production is a human step), and a bucket the code depends on must not wait for one. No size cap or MIME allow-list on the bucket, because either could strand a legacy object mid-move. The name is a constant, not an environment variable — nothing to add to `DEPLOYMENT.md`'s table (B11), and nothing to get wrong per deployment.
- **Copy, verify, then delete — never the other way round.** Per object: read the public copy with the service key (the authenticated route, not the CDN) and check it against the listing's size and MD5 etag; write it to the private bucket CREATE-ONLY; read the private copy back and compare length and SHA-256; only then delete the public copy. If the private key already holds different bytes (e.g. a comment edited after the deploy, which lands privately), neither is overwritten: the public bytes are parked at `legacy-conflicts/<key with a hash>` (create-only, read back, compared) and then the public copy is deleted. Any failure at any step leaves the public copy for the next run.
- **Idempotent, concurrent, interruptible.** All writes are create-only, so re-runs and parallel runs converge: a verified private copy beside an untouched public one is finished by the next run without a second write. A run over an empty legacy prefix lists and does nothing.
- **Nothing disappears mid-move.** Until an object has moved, `CaptureStore` lists both buckets as one and reads through to the public copy (with the key), and a delete removes both copies — otherwise the migration would carry a deleted row straight back.
- **The legacy handle is fenced.** It can read, list and delete only keys under `dev-flags/` and `dev-queue/` in `card-art`, and cannot write at all; it cannot address a catalog image. If configuration ever pointed it at the private bucket itself, it is dropped, since "delete the old copy" would then delete the only one.

**Why:** The routes were gated but the objects were not. `card-art` is the public catalog-art CDN, and these object names are millisecond timestamps, so anyone who guessed one could read a photograph taken in the owner's house straight from Supabase, no sign-in. The owner asked for the fix. These are the owner's labelled training data, so the move is built around one rule: losing an object is worse than one staying public a while longer — a public object is deleted only after a byte-identical private copy has been read back.

Where the move runs: behind the labeler gate, driven by the labeler pages. Not on the listing requests (a 20-second batch in front of every queue list would make the labeler crawl for the whole move), not on a cron (nothing in this deployment runs on a schedule without adding a secret, and the Vercel config change would need its own approval under B9), not at build time (a build runs for every preview as well, and a build step that moves stored data is a different kind of change from a deploy). The accounts that can call it are exactly the accounts whose captures these are, and they open these pages in normal use, so no operator step is needed. Queued photos move under the queue's own family advisory lock (queue-state.md), the lock discard already holds.

**Implications:**
- After the deploy, the public copies stay public until an entitled account first opens `/dev/quad-labeler` or `/dev/quad-harvest`; that visit moves them (20 s batches, looped by the page). Nothing else starts it.
- A deployment built from an older branch (an open PR's preview, a rollback) still reads and writes `card-art/dev-*` and will not see moved captures. Anything such a deployment writes publicly is picked up by the next run of the move, which is why the read-through and the migration stay in the code rather than being one-shot.
- One narrow race is accepted and documented: an owner DELETE of a `dev-flags/` row landing in the second that same object is being moved can leave the private copy behind (the row reappears and can be deleted again). It cannot go the other way. Queue objects do not have it (family lock).
- Objects parked under `legacy-conflicts/` are listed by nothing; they exist so a human can still answer "which copy was right" in the Supabase dashboard.
- Captures keep the class-level provenance they had (`CaptureStore.put` demands the provenance and reason, as `putUnmanifestedObject` did); they were never `image_asset` rows. Their leaving `card-art` also removes them from `manifest:check --object-store`'s unrecorded-object list.
- Tests: `packages/storage/src/__tests__/capture-migration.test.ts` and `capture-store.test.ts` (fake storage: copy-verify-delete, verification failure keeps the public copy, stale reads, re-run no-op, interrupted run, conflicts, concurrent runs, budget, the fenced legacy handle, bucket create/refuse), `apps/api/src/dev/__tests__/privateCaptures.test.ts` (routes over the private store), `apps/web/src/scan/labeler/__tests__/captureMigration.test.ts` (the drain loop; no public capture URL anywhere in the web app), and the `queue` browser suite asserts both labeler routes start the move.
