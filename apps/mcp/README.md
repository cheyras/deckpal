# deckpal-mcp

DeckPal's MCP server: 28 tools (17 read, 11 write) that let an AI app read and
change a DeckPal collection, its decks, lists and battle logs. Claude is tested
end to end; ChatGPT and other apps with remote MCP connectors should work from
what their docs say, but have not been tested. The tools are defined once in
`@deckpal/agent-tools` and shared with Deck-E, the in-app assistant.

- **Cloud:** `https://deckpal.app/mcp`, multi-user, OAuth 2.1 or a personal
  access token. Entry point `src/cloud.ts`.
- **Self-host:** one user, one process on `127.0.0.1:3704`, behind a shared
  key. Entry point `src/index.ts`.
- **The full tool reference** — every argument, default and annotation — is
  [`TOOLS.md`](TOOLS.md), generated from the registry. The design spec is
  [`SPEC.md`](SPEC.md).

## Connect

### Claude (claude.ai and Claude Desktop)

1. Customize → Connectors → **Add custom connector**. Name it DeckPal, paste
   `https://deckpal.app/mcp` as the server URL, leave the advanced settings
   empty, and click **Add**.
2. Click **Connect**. Sign in to DeckPal if asked; a new account confirms its
   email first.
3. On DeckPal's consent page choose **Read and change** or **Read only**, then
   **Allow**.
4. Turn DeckPal on in a chat's tools menu.

### Claude Code

```bash
claude mcp add --transport http deckpal https://deckpal.app/mcp
```

Then run `/mcp`, pick deckpal and finish sign-in in the browser. The browser
step needs a desktop session: on a headless or SSH machine use a personal
access token instead (below).

### ChatGPT

In a ChatGPT plan that allows custom connectors, add a connector (developer
mode) with the URL `https://deckpal.app/mcp` and OAuth authentication. ChatGPT
registers itself, and DeckPal's consent page shows its callback host as
**Unverified** — only Claude's callbacks (on claude.ai and claude.com) are on
DeckPal's verified list — so
check that the host is ChatGPT's before allowing. This path has not been tested
end to end; report what you see.

### Any other client: a personal access token

DeckPal → Profile → **Agent access** → **New token**. Choose **Read and change**
(the default) or **Read only**, then copy the token when it is shown; it is
shown once. Send it on every request:

```json
{
  "mcpServers": {
    "deckpal": {
      "type": "http",
      "url": "https://deckpal.app/mcp",
      "headers": { "Authorization": "Bearer dsk_your_token" }
    }
  }
}
```

### Self-host

Run the API, then the server with a shared key, and send the key as
`x-brain-key`. The full runbook (database, migrations, catalog, proxy) is in
[`DEPLOYMENT.md`](../../DEPLOYMENT.md).

```bash
pnpm --filter @deckpal/db build && pnpm --filter @deckpal/agent-tools build && pnpm --filter deckpal-mcp build
DECKPAL_MCP_KEY=<a long random string you keep> DECKPAL_API_BASE=http://127.0.0.1:3700/deckpal/api node apps/mcp/dist/index.js
```

`DECKPAL_API_BASE` must name the path the API actually mounts on. A self-host
behind nginx at `/deckpal/` deletes `API_BASE_PATH` from the `.env` copied from
`.env.example`, so the API uses its default `/deckpal/api` (as above). If you
keep `.env.example`'s `API_BASE_PATH=/api`, use
`DECKPAL_API_BASE=http://127.0.0.1:3700/api` instead.

The socket only binds 127.0.0.1, and only `MCP_ALLOWED_HOSTS` (default
`127.0.0.1,localhost`) pass the host check, so a hosted client reaches it
through your TLS proxy, which can also inject the header.

## Tokens

| | OAuth connection | Personal access token | Self-host key |
|---|---|---|---|
| How you get it | the client's Connect button | Profile → Agent access | `DECKPAL_MCP_KEY` |
| Sent as | `Authorization: Bearer` (the client handles it) | `Authorization: Bearer dsk_…` | `x-brain-key: …` |
| Scope | Read and change, or Read only — chosen on the consent page | Read and change, or Read only — chosen when you create it | everything (one user) |
| Lifetime | access token 1 hour, refresh token 90 days, rotated on use | until revoked | until you change it |
| Revoke | Profile → Agent access | Profile → Agent access | restart with a new key |

- **Stored as a hash.** DeckPal keeps only SHA-256 of a token, so a lost
  token cannot be recovered; make a new one.
- **Don't put a token in the URL path.** `https://deckpal.app/mcp/dsk_…` still
  works for connectors set up that way long ago, but request paths land in
  server logs. Use the header.
- **What an invalid token gets.** A missing token is told how to connect. An
  expired or revoked one gets a 401 with `error="invalid_token"`, which tells
  an OAuth client to refresh.
- **Rate limits.** 60 requests a minute per token, answered with 429 and
  `Retry-After: 60`.

A **Read only** connection or token is shown the read tools and nothing else,
runs in a read-only transaction, and is refused any write at the REST API too. The server
instructions tell the model what that means (if `save_deck` is missing, give the
user the text instead).

How the writes behave:

- **Every write previews first.** `dry_run` defaults to true, so the first call
  shows what would change and writes nothing; the model shows that to the user
  and repeats the call with `dry_run: false` after a yes. The one exception is
  `deck_strategy`, which has no preview and says so in its description.
- **A preview is a default, not a gate.** A client that sends `dry_run: false`
  on the first call writes on the first call. What stands between a model and a
  write is the client's approval prompt; every write tool is advertised with
  `readOnlyHint: false` and an explicit `destructiveHint`, so clients that ask
  before writes will ask.
- **Undo.** Collection changes, list changes, deck deletes and strategy-guide
  rewrites are recorded in `mutation_history` and can be undone with `revert`
  (dry run first; an item that cannot be undone exactly is reported, never
  half-applied). Decks and lists go to a recycle bin when deleted; `purge`
  skips it.
- **What cannot be undone.** A deck's card list is versioned once it has battle
  logs (`deck_history` restores a version); an edit to a version with no logs
  replaces it in place. Battle-log edits and deletes cannot be undone, and
  battle-log writes made over MCP are not in `mutation_history`. The
  2026-10-12 decision `decisions/2026/2026-10-12-mcp-tool-surface-and-write-safety.md`
  has the full table and the options for closing these gaps.
- **Text from other people.** Opponent screen names and card names come out of
  pasted battle logs and are written by the other player's client. Tools print
  them as quoted values when they do not look like ordinary names, fence raw
  logs, and strip invisible characters. The server instructions tell the model
  they are data, not instructions.

## Example sessions

Real output from `pnpm mcp:audit --responses`, which calls every read tool —
plus the write tools that build its fixture (`log_cards`, `save_deck`,
`add_battle_log`, `deck_strategy`, `edit_list`, `revert`) — against a seeded
database. It does not call `delete_deck`, `delete_list`, `edit_battle_log` or
`delete_battle_log`. The deck and card names are real; the collection is
synthetic.

### Logging a pasted PTCG Live game

The user pastes a log without naming a deck. `add_battle_log { log, player_name }`
ranks their decks and writes nothing:

```text
Nothing was logged.
WIN vs zoroark.main (Fezandipiti ex) | 7 turns | prizes 2-0 | confidence high
Ranked candidate decks (best first):
41f2b41d-… | Dhelmise testing 2 | v1 | standard | score 21 | matched 11/22
c5ba09fa-… | Dhelmise (dhelmise-pbl) | v1 | standard | score 21 | matched 11/22
…
Call add_battle_log again with deck_id set to the one you mean (or dry_run: true to preview the log first).
```

The user names the deck. The same call with `deck_id` previews; after a yes,
`dry_run: false` logs it:

```text
Would attach to 'Dragapult (dragapult-ex)' (v6): WIN vs zoroark.main (Fezandipiti ex) | 7 turns | prizes 2-0 | confidence high
Nothing was logged.
Re-run with dry_run: false to log this game.
```

```text
Logged battle #121 → attached to v6 (the deck's current version).
WIN vs zoroark.main (Fezandipiti ex) | 7 turns | prizes 2-0 | parser confidence high
v6 record: 11W–10L–0T (21 log(s))
```

To review it, `battle_digest { deck_id, log_id: 121 }` returns the game in
about 1,200 characters instead of the 4–15k of the raw log:

```text
battle digest #121 | v6 | 'Dragapult (dragapult-ex)' | stored result WIN
players: me AuditTrainer vs zoroark.main
… | 7 turns (me 4, opp 3) | went first: me | mulligans: me 0, opp 6
first attack damage: me T3, opp never
prizes taken: me 2 – opp 0 · not close (gap 2)
…
unknown (never guess these): the opponent's hand, and any card of theirs that was never shown; which cards were prized, on either side
```

### A write, and undoing it

`log_cards { items: [{ card_id: "me02-014", delta: 1 }], note: "pulled from a booster" }`
previews:

```text
log_cards DRY RUN — 1 item(s)
#1 Moltres | me02-014 | normal | 1 → 2 (Δ+1)
would apply 1, unchanged 0, skipped 0 (unresolved/invalid)
dry run — nothing written; re-call with dry_run:false to apply
```

With `dry_run: false` it writes, and says how to undo it:

```text
log_cards — 1 item(s)
#1 ✓ Moltres | me02-014 | normal | 1 → 2 (Δ+1)
     set me02: complete 29/130 (22.3%) · master 29/236 (12.3%) · grandmaster 29/236 (12.3%)
applied 1, unchanged 0, skipped 0 (unresolved)
batch id fedd6611-… — undo with revert(batch_id: "fedd6611-…")
```

`revert { batch_id }` previews the undo, and `dry_run: false` applies it (and is
itself undoable):

```text
revert — batch fedd6611-… ("pulled from a booster") (strategy: inverse)
  ✓ #1369 | collection_item | 673 | quantity 2 → 1
undid 1, 0 conflict(s) left alone, 0 skipped
this revert is itself operation bbd779ac-… — revert(batch_id: "bbd779ac-…") undoes it
```

## Measuring the surface

```bash
pnpm mcp:audit               # tools/list: size of every tool, and the per-turn total
pnpm mcp:audit --responses   # also every read's result size, on a seeded disposable database (Linux/WSL)
pnpm mcp:tools-doc           # regenerate TOOLS.md and the tool list above
```

The database CI job runs the `--responses` half with budgets on, so a read
that grows past its cap fails the build. On 2026-10-12, `tools/list` was about
66,600 characters (~16.7k tokens) plus 3,965 characters of server instructions.
